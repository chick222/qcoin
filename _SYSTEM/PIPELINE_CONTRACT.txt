NUM 4 — PIPELINE_CONTRACT
Версия 3.2 — USER-DEFINED DIAGNOSTIC REGION + PREALIGN

НАЗНАЧЕНИЕ
Этот файл — единственный технический контракт RUN, машинных шлюзов, REWORK/HARD_STOP и VERDICT_RECEIPT.
Он не заменяет нумизматическую методику ОБЩЕЙ_ИНСТРУКЦИИ, инструкции номиналов и SPEC.

1. РОЛИ
ORCHESTRATOR — фиксирует входы/канонические источники, ведёт RUN и запускает стадии; сам не выбирает разновидность.
GEOMETER — сначала выполняет PREALIGN по краю монеты (круг/эллипс → круг), затем ориентирует по общим недиагностическим контурам полного эталона, после этого на нормализованной копии находит утверждённые C1–C3 и независимые validation points; не анализирует диагностический признак.
MACHINE_GATE — num_pipeline.py; машинный PASS нельзя заменить текстовым утверждением модели.
DIAGNOSTICIAN — работает только с геометрически разрешёнными артефактами и утверждёнными diagnostic_region; не меняет геометрию.
AUDITOR — пытается отклонить вывод, проверяя цепочку, неизменность артефактов и исключение ближайшей существенной альтернативы; сам ничего не «подправляет».

2. ОБЯЗАТЕЛЬНЫЕ СОСТОЯНИЯ
SOURCES_PASS -> BRANCH_PASS -> PREALIGN_PASS -> GEOMETRY_PASS -> DIAGNOSTICS_PASS -> ALTERNATIVES_PASS -> AUDIT_PASS -> VERDICT_RECEIPT.
Любой отсутствующий PASS, REWORK или HARD_STOP блокирует VERDICT_RECEIPT и downstream-этапы.

3. СТАТИЧЕСКИЕ И ДИНАМИЧЕСКИЕ ДАННЫЕ
Статические данные ветки:
- SPEC.txt хранит канонический нумизматический смысл признаков, точек и областей;
- GEOMETRY_GATE.json рядом с конкретным SPEC/эталоном хранит машиночитаемый технический конфиг;
- GEOMETRY_GATE.json не может переопределять SPEC;
- изменение SPEC/эталона требует повторной привязки хэшей и проверки binding.

Динамические данные монеты:
- хранятся только в /coins4/_RUNS/<RUN_ID>/;
- одна физическая монета = один RUN, включая дополнительные диагностические фотографии;
- RUN_ID нейтрален и не кодирует неподтверждённую разновидность.

4. ACTIVE RUN И ЖИЗНЕННЫЙ ЦИКЛ
Глобальный указатель: /coins4/_RUNS/ACTIVE_RUN.json.
Одновременно допустим не более одного status=ACTIVE.
RUN-папка не перемещается между ACTIVE/DONE/ABORTED: статус хранится в manifest.json/run_state.json; после закрытия папка остаётся /coins4/_RUNS/<RUN_ID>/.

INIT:
1) снять полный snapshot /coins4/inbox: Drive ID, имя, размер, SHA-256 каждого файла;
2) выполнить num_pipeline.py init-run <snapshot> <local_run_dir>;
3) PASS создаёт manifest.json и run_state.json;
4) записать их в /coins4/_RUNS/<RUN_ID>/ и обновить ACTIVE_RUN.json pointer-ом результата;
5) проверить запись; только после этого разрешён GEOMETER.
RUN_INIT STOP блокирует атрибуцию.

SYNC:
- при каждом продолжении той же монеты заново фиксировать полный текущий набор inbox;
- выполнить num_pipeline.py sync-run-inputs <run_dir> <snapshot>;
- новые ID добавляются в существующий manifest; новый RUN не создаётся;
- исчезновение/изменение ранее известного ID/размера/SHA-256 => STOP;
- добавление новых входов сбрасывает downstream gates в PENDING и rework_counters, сохраняя review_history.

CLOSE:
- close-run --mode VERDICT требует verdict.json с PASS и VERDICT_RECEIPT;
- close-run --mode ABORT завершает RUN без вердикта;
- успешное закрытие выдаёт ACTIVE_RUN pointer со status=NONE.

5. ДИНАМИЧЕСКИЕ АРТЕФАКТЫ RUN
ORCHESTRATOR создаёт их автоматически по мере прохождения стадий:
- inbox_snapshot.json — snapshot входных фото для INIT/SYNC;
- manifest.json — входные файлы и канонические источники;
- run_state.json — состояние gates, workflow и история review;
- prealign_<reference>.json — контур, его нормализация до круга, ориентировка по общим контурам, прямое/обратное преобразование, SHA-256 рабочей копии и machine receipt;
- geometry_proposal_<zone>.json — точки на нормализованной копии и provenance финального преобразования;
- geometry_gate_<zone>.json — прямой машинный результат validate-geometry;
- diagnostics.json — наблюдения после всех требуемых GEOMETRY_PASS;
- alternatives.json — проверка ближайших существенных альтернатив;
- audit.json — итог аудита цепочки и выводов;
- review_decision_<NNN>.json — каждый маршрут отрицательного review и последующий clearing PASS;
- verdict.json — только из успешного verdict-receipt.

Шаблоны /coins4/_SYSTEM/PIPELINE_TEMPLATES/ задают формат и никогда не являются PASS/доказательством.

6. GEOMETRY_GATE — ОБЯЗАТЕЛЬНЫЙ КОНТРАКТ
Для каждой реально сравниваемой диагностической зоны:
- ровно три C1–C3 задают только геометрическое совмещение;
- единственная диагностическая область задаётся полем zones[].diagnostic_region;
- пользовательская форма не ограничена polygon: допускается свободный контур, лассо, закрашенная область или иная однозначная ручная выборка на полном эталоне;
- перед записью в конфиг любая такая область канонизируется в binary mask полного canvas;
- каноническое машинное представление: diagnostic_region.type=BINARY_MASK_RLE, canvas=[width,height], runs=[[start,length],...], source=USER_MARKUP_FULL_REFERENCE, approved=true;
- runs — непустые непересекающиеся интервалы положительной длины в row-major нумерации пикселей полного холста;
- прямоугольные diagnostic_roi/ROI, FULL_ROI, отдельные diagnostic_mask и diagnostic_polygon как обязательная форма в активном конфиге запрещены как legacy;
- bbox C1–C3 не ограничивает diagnostic_region;
- технический bounding box/crop разрешено вычислять только временно из маски и нигде не считать диагностической зоной;
- предварительная нормализация исходного кадра до C1–C3 строится из измеренного края (форма) и общих недиагностических контуров (ориентация); её отдельный шлюз обязателен;
- ФИНАЛЬНОЕ преобразование между нормализованной монетой и эталоном строится только из C1–C3 по разрешённой модели;
- после фиксации ОБОИХ преобразований любые дополнительные warp/resize/rotation/affine/perspective запрещены;
- область текущей монеты получается только применением прошедшего геометрического преобразования к канонической diagnostic_region;
- DIAGNOSTICIAN учитывает только содержимое внутри преобразованной области.

Обязательные поля статического GEOMETRY_GATE.json:
schema_version
canonical_spec_file_id
canonical_spec_sha256
reference_file_id
reference_sha256
canvas
transform_model
post_transform_policy=FORBID
max_control_residual_px
max_validation_residual_px
max_allowed_deformation
zones[].id
zones[].reference_points
zones[].diagnostic_region
zones[].validation_points[].id
zones[].validation_points[].description
zones[].validation_points[].reference

ШЛЮЗ ДИАГНОСТИЧЕСКОЙ ОБЛАСТИ:
- если diagnostic_region отсутствует/TBD => CONFIG_MISSING => HARD_STOP до ручной разметки пользователем;
- если region не BINARY_MASK_RLE, не approved, имеет неверный canvas, пустую/перекрывающуюся/out-of-range RLE-маску => REGION_INVALID => HARD_STOP;
- наличие legacy-полей diagnostic_roi, roi_must_be_strictly_inside_control_bbox, diagnostic_mask или diagnostic_polygon => LEGACY_DIAGNOSTIC_ZONE_FIELD => HARD_STOP до обслуживания;
- diagnostic_region нельзя выводить из старого прямоугольника автоматически; её источник — ручное пользовательское выделение на полном эталоне с последующим подтверждённым переносом на альтернативы.

TBD-ПРАВИЛО:
Никакое значение допуска, модель преобразования, контрольная/validation point, diagnostic_region или смысл признака не придумываются во время атрибуции.
Неутверждённое обязательное поле остаётся TBD => CONFIG_MISSING/CONFIG_INVALID => HARD_STOP до обслуживания ветки.


6А. ОБЯЗАТЕЛЬНЫЙ PREALIGN — КОНТУР → КРУГ → ОРИЕНТАЦИЯ → C1–C3
Это предшествующая стадия внутри GEOMETER, а НЕ замена утверждённого GEOMETRY_GATE. Порядок обязателен для всех сравнений с полным эталоном:
A. По неизменённой фотографии текущей монеты определить реальный внешний круглый край, измерить контур, эллипс/круг, центр, полуоси, угол осей, ошибку подгонки и пригодность. Не брать за край тень или рельеф. Неизмеримость края без угадывания — PREALIGN_STOP, запрос нужного фото только после проверки всех необходимых зон.
B. При обоснованном эллиптическом съёмочном искажении ПЕРЕД поиском C1–C3 исправить эллипс до окружности ОДНОЙ глобальной предварительной коррекцией, рассчитанной ТОЛЬКО по внешнему краю. Если контур уже круглый, матрица коррекции тождественна; нет основания для произвольной перспективной/аффинной подгонки рельефа.
C. На округлённой копии выполнить предварительную ориентировку поворотом/сдвигом по общим НЕдиагностическим контурам полного канонического эталона. Нельзя использовать отличающие штемпель признаки, diagnostic_region, SSIM-вариантность или ориентировку «под выбранную разновидность»; для альтернатив подготовку документировать независимо.
D. Зафиксировать prealign.json в RUN: input_file_id и raw_sha256; reference_file_id; сырую маску/параметры измеренного края и её хэш; тип коррекции; raw_to_normalized и normalized_to_raw (взаимно обратимые матрицы); нормализованные размеры, normalized_sha256; параметры/ориентиры поворота; результаты проверки круглости и соответствия общих контуров; идентификатор алгоритма/версии. Матрицы должны описывать ФАКТИЧЕСКИ созданную рабочую копию. Один и тот же prealign должен быть воспроизводим по привязанным входным байтам.
E. Только после явного PREALIGN_PASS находить C1–C3 и validation points на нормализованной фотографии. Формировать финальный `SIMILARITY_LS_3PT` из ТЕХ ЖЕ физически соответствующих точек. Контрольные и validation residuals вычислять ПОСЛЕ финальной регистрации в координатах полного эталона (3 px и 6 px для действующих веток).
F. Геометрия полного пути есть `T_final = T_C1C2C3 ∘ T_prealign`; обратная маска `diagnostic_region` применяется по обратному ПОЛНОМУ пути к raw-фото либо напрямую по `T_C1C2C3^-1` к неизменной нормализованной копии. Не преобразовывать диагностическую маску вручную, не делать локальных warps и не терять состояние координат.
G. MACHINE_GATE должен проверять prealign receipt и привязку нормализованного снимка к исходному, математическую совместимость/обратимость обеих матриц, допустимость модели коррекции, качество округления края, независимый тест общих ориентиров, наличие необходимых provenance-хэшей, затем строгие C1–C3/validation checks. Несохранённый/непроверенный prealign НЕ даёт GEOMETRY_PASS, даже если точки формально проходят допуски.
H. Любое исправление prealign повторяет этапы D–G и инвалидирует привязанные downstream артефакты, но НЕ стирает прежние ошибки, review_history и rework counters. Нельзя пересоздавать RUN ради обхода лимита.

Техническая граница: неравномерная коррекция относится только к измеренному внешнему эллипсу в PREALIGN; утверждённая final `SIMILARITY_LS_3PT` не разрешает анизотропную деформацию и не должна заменяться AFFINE/PERSPECTIVE без отдельного изменения канонического конфига. Любые спорные измерения дают PREALIGN_REWORK/STOP, а не искусственный PASS.

СОВМЕСТИМОСТЬ/АКТИВАЦИЯ. Это изменение контракта применяется после приведения num_pipeline.py, соответствующих шаблонов и тестов к prealign-схеме и проверки машинного контроля. Старые протоколы без prealign receipt автоматически не считаются PASS; текущий RUN сохраняется с его historical decisions. При отсутствии реализованного PREALIGN_GATE атрибуция не продолжается фиктивной отметкой PASS — сначала обновить техническую реализацию.

7. REVIEW ROUTER
Любой отрицательный результат обязательного цензора до дальнейших действий передаётся:
num_pipeline.py route-review <run_dir> <review.json>

Результаты маршрутизатора:
PASS — тот же reviewer + failed_stage принял исправленный результат; активная блокировка снимается, затронутый aggregate gate возвращается в PENDING для штатного повторного вычисления.
REWORK — дефект исправим внутри текущего RUN без изменения канонических источников и без новых внешних данных.
HARD_STOP — внутренней роли запрещено продолжать; требуется внешнее/каноническое изменение либо расследование.
Неизвестный reason_code всегда fail-closed => HARD_STOP.
PASS другого reviewer/этапа не снимает активный REWORK/HARD_STOP.

8. REWORK
Типичные REWORK:
- неверные/неполные точки текущей монеты;
- запрещённое post-transform;
- residual/deformation выше утверждённого порога;
- неполное диагностическое обоснование;
- ближайшая существенная альтернатива не исключена при наличии достаточных текущих данных.

При REWORK:
- RUN остаётся тем же;
- REVIEW_ROUTER задаёт target_stage;
- gates от затронутого этапа вниз инвалидируются;
- создаётся review_decision_<NNN>.json;
- работа явно возвращается указанной роли;
- после переделки тот же reviewer + failed_stage обязан проверить новый артефакт заново.

Лимит: максимум 3 автоматических возврата одного defect_signature. Следующее отклонение => HARD_STOP + REWORK_LIMIT_EXCEEDED.

9. HARD_STOP
Типичные HARD_STOP:
- CONFIG_MISSING / CONFIG_INVALID;
- противоречие SPEC и GEOMETRY_GATE;
- SPEC_HASH_MISMATCH / REFERENCE_HASH_MISMATCH;
- отсутствующий обязательный канонический источник;
- исчезновение/изменение известных input-файлов;
- повреждение/несовпадение хэша артефакта;
- недостаточное фото или обязательное измерение, которое нельзя получить из текущих данных;
- неизвестная непредусмотренная причина;
- REWORK_LIMIT_EXCEEDED.

При HARD_STOP:
- downstream работа прекращается;
- RUN сохраняется для продолжения после устранения причины;
- VERDICT_RECEIPT/вердикт запрещены;
- канонические данные не «исправляются» внутри диагностики;
- продолжение возможно только после выполнения resume_condition и повторного прохождения проваленного шлюза.

10. REVIEW_DECISION И СООБЩЕНИЕ ПОЛЬЗОВАТЕЛЮ
Каждое решение маршрутизатора фиксируется в review_decision_<NNN>.json и run_state.review_history.
Для отрицательного решения обязательны:
reviewer
failed_stage
result = REWORK | HARD_STOP
reason_codes[]
issues[]
detailed_reason
returned_for_rework
return_note
target_stage (REWORK)
rework_attempt / max_rework_attempts
invalidated_gates[]
resume_condition
user_action_required
review_sha256
updated_at

При каждом REWORK/HARD_STOP ORCHESTRATOR немедленно сообщает пользователю те же существенные данные:
- кто отклонил и что проверялось;
- точные reason_codes;
- детальную фактическую причину, включая observed/threshold/unit, если они есть;
- какие gates инвалидированы;
- REWORK: явную фразу «ВОЗВРАЩЕНО НА ПЕРЕДЕЛКУ», target_stage и попытку N/3;
- HARD_STOP: явную фразу «РАБОТА ОСТАНОВЛЕНА» и почему внутренний возврат невозможен;
- точное resume_condition.
Сообщения вида «геометрия плохая» или «аудит не прошёл» без причины запрещены.

10А. ДВА СЛОЯ ПОЛЬЗОВАТЕЛЬСКОГО ОТЧЁТА
Внутренний машинный журнал остаётся подробным, но пользовательский ответ по умолчанию имеет два слоя.
Слой 1 — обязательный человекочитаемый итог, максимум несколько коротких абзацев:
1) что уже установлено по монете;
2) PASS / ВОЗВРАЩЕНО НА ПЕРЕДЕЛКУ / ПРОВЕРКА ОСТАНОВЛЕНА — обычными словами;
3) причина без кодов;
4) следующее действие системы или одна конкретная просьба к пользователю.
Слой 2 — «Технические детали» только после слоя 1 и только в объёме, полезном для диагностики: RUN_ID, failed_stage, reason_codes, observed/threshold, invalidated_gates, resume_condition.
Нельзя выдавать машинный JSON/список полей вместо слоя 1.
Если HARD_STOP относится к канонической конфигурации ветки, а не к фотографии текущей монеты, это надо прямо сказать пользователю.
Если проблема может быть устранена обслуживанием каталога без новых данных пользователя, пользовательский ответ должен прямо сообщать, что от пользователя сейчас ничего не требуется и следующим действием является обслуживание каталога.

11. VERDICT_RECEIPT
num_pipeline.py verdict-receipt выдаёт PASS только если:
- workflow_status не REWORK/HARD_STOP;
- все обязательные gates = PASS;
- state относится к текущему RUN и его зафиксированным артефактам.
Текстовый вердикт без действительного VERDICT_RECEIPT недействителен.
